
# Конфигурация виртуальной машины `devops-vm`

## 1. Параметры машины

- **Операционная система:** Ubuntu 22.04.5 LTS.
- **Оперативная память:** 2 ГиБ.
- **Количество виртуальных процессоров:** 2.
- **Размер виртуального диска:** 25 ГБ.
- **Размер корневого логического тома:** 11,5 ГБ.
- **Архитектура:** x86-64.
- **Гипервизор:** Oracle VirtualBox.

## 2. Сетевые интерфейсы

- **`enp0s3`** — интерфейс NAT с IP-адресом `10.0.2.15/24`. Шлюз по умолчанию: `10.0.2.2`.
- **`enp0s8`** — интерфейс Host-only с IP-адресом `192.168.79.101/24`.
- **`lo`** — локальный интерфейс с IP-адресом `127.0.0.1`.

## 3. Правила проброса портов

Настроен проброс TCP-соединений с хостовой системы на SSH-службу виртуальной машины.

- **Windows:** `127.0.0.1:2222` → `2222` гостевой системы.
- **Mac:** `192.168.1.72:2223` → `2222` гостевой системы.

SSH-служба внутри виртуальной машины использует порт `2222`.

## 4. Учётные записи

- **Пользователь:** `devops`.
- **UID:** `1001`.
- **Основная группа:** `devops` (GID `1001`).
- **Дополнительная группа:** `sudo`.
- **Способ удалённой аутентификации:** SSH по публичным ключам.
- **Парольная аутентификация по SSH:** отключена.
- **Вход пользователя `root` по SSH:** запрещён.

## 5. Служба SSH

- **Порт:** `2222`.
- **Файл конфигурации:** `/etc/ssh/sshd_config`.
- **Разрешённые пользователи:** `devops`.
- **`PermitRootLogin`:** `no`.
- **`PasswordAuthentication`:** `no`.
- **`MaxAuthTries`:** `3`.
- **Способ аутентификации:** SSH-ключи.

## 6. Правила межсетевого экрана

Используется UFW. Межсетевой экран активен.

Политики по умолчанию:
- Входящие соединения: `deny`.
- Исходящие соединения: `allow`.
- Маршрутизируемые соединения: `disabled`.

Правила:
- `80/tcp` — HTTP, разрешён.
- `443/tcp` — HTTPS, разрешён.
- `2222/tcp` — SSH, ограничение частоты подключений (`LIMIT`).

Правила настроены для IPv4 и IPv6.

## 8. Веб-сервер

- **Пакет:** Nginx (`nginx`), версия 1.18.0.
- **Конфигурация ресурса:** `/etc/nginx/sites-available/devops-site`.
- **Активная конфигурация:** `/etc/nginx/sites-enabled/devops-site`.
- **Каталог ресурса:** `/var/www/devops-site`.
- **Владелец каталога и файлов:** `devops:devops`.
- **Права каталогов:** `755` (`drwxr-xr-x`).
- **Права HTML-файлов:** `644` (`-rw-r--r--`).
- **Сертификат:** `/etc/ssl/certs/devops.crt`, владелец `root:root`, права `644`.
- **Закрытый ключ:** `/etc/ssl/private/devops.key`, владелец `root:root`, права `600`.
- **Срок действия сертификата:** 365 дней, с 21 октября 2026 года по 21 октября 2027 года.

### Формирование сертификата

```bash
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/devops.key \
  -out /etc/ssl/certs/devops.crt \
  -subj "/CN=devops.local" \
  -addext "subjectAltName=DNS:devops.local"
```

Сертификат самоподписанный. Поле Subject Alternative Name содержит DNS-имя `devops.local`.

## 9. Контейнеризация

На сервере установлен Docker Engine **29.9.2** и настроен Docker Compose. Пользователь `devops` входит в группу `docker`.

Приложение размещено в `/home/devops/app` и запускается из образа `devops-app:1.0`. Для базы данных используется `postgres:16-alpine`.

- **Конфигурация:** `docker-compose.yml`.
- **Переменные окружения:** `.env`, права доступа `600`. Файл содержит секреты и не должен попадать в Git.
- **Порт приложения:** `127.0.0.1:5000`, доступен только через локальный интерфейс сервера.
- **База данных:** PostgreSQL, порт `5432` внутри Docker-сети, без публикации на хосте.
- **Хранение данных:** именованный Docker-том `app_db_data`.

Для доступа к приложению через HTTPS используется Nginx. Запросы к `https://devops.local/app/` проксируются на `127.0.0.1:5000`. Nginx передаёт заголовки с информацией о хосте, клиенте и исходном протоколе.

### Основные команды

```bash
# Проверка версий
docker --version
docker compose version

# Переход в каталог приложения
cd ~/app

# Запуск и проверка контейнеров
docker compose up -d
docker compose ps

# Просмотр томов
docker volume ls

# Проверка прав доступа к секретам
stat -c '%a %n' ~/app/.env

# Остановка и повторный запуск приложения
docker compose stop app
docker compose start app

# Остановка контейнеров
docker compose down
```

Команда `docker compose down -v` удаляет связанные именованные тома и может привести к потере сохранённых данных, поэтому используется только при намеренном сбросе данных.

## 10. Ansible

### 10.1. Расположение проекта и узлы

Проект Ansible находится в GitHub-репозитории devops,
локальный путь: ~/devops/ansible.

Управляющий узел:
- MacBook с macOS.
- Установлены Ansible и sshpass.
- На управляющем узле находятся inventory, playbook,
  роли и SSH-ключ.

Управляемый узел:
- Виртуальная машина devops-vm.
- Ubuntu 22.04.5 LTS, архитектура x86_64.
- Виртуальная машина запущена в VirtualBox на Windows-компьютере.

Подключение выполняется по SSH через проброс портов VirtualBox:
- IP Windows-компьютера: 192.168.1.79.
- Внешний SSH-порт: 2223.
- SSH-порт виртуальной машины: 22.

### 10.2. Inventory и учётные записи

Для первоначальной настройки используется bootstrap.ini:
- Пользователь: student.
- Подключение по SSH с парольной аутентификацией.
- Пароль вводится интерактивно.

Для последующих запусков используется prod.ini:
- Пользователь: devops.
- Подключение по SSH-ключу ~/.ssh/devops_vm.
- Sudo настроен без интерактивного ввода пароля.

Файл ansible.cfg определяет prod.ini как inventory
по умолчанию.

### 10.3. Роли Ansible

В проекте реализованы четыре роли:

- base — проверка ОС, установка базовых пакетов,
  Docker Engine и настройка службы Docker.
- ssh — создание пользователя devops, установка
  SSH-ключа, настройка sudo и UFW, усиление безопасности SSH.
- nginx — установка Nginx и настройка reverse proxy
  для приложения.
- app — загрузка Docker-образа из GHCR, запуск
  контейнера и проверка его работоспособности.

### 10.5. Запуск и проверка

Первоначальная настройка сервера:

cd ~/devops/ansible

ansible-playbook -i inventory/bootstrap.ini site.yml --ask-pass --ask-become-pass

Повторный запуск через prod inventory:

ansible-playbook site.yml

Автоматический аудит конфигурации:

ansible-playbook verify.yml

При отсутствии изменений повторный запуск основного
playbook должен завершаться с changed=0 и failed=0.

Read-only аудит также должен завершаться с changed=0.
